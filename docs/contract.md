# 配方核算契约

采购员输入 ingredients、recipes、orders 三个数组，厨师复核每条订单的配料来源路径。所有质量为克，金额使用同一调用者自定货币；数值输入为最多9位整数、6位小数的十进制字符串，精确有理数输出用整数或 n/d 字符串。

ingredient：唯一 id、yield (0,1]、price_per_gross_gram >=0、唯一 tags 数组。yield 将需用净料折算为采购毛料，trim 为这一步的损耗。标签只做原声明传播，不代表食品过敏安全判定。

recipe：唯一 id、正 output_grams、components。组件 kind 为 ingredient 或 recipe，ref 必须存在，net_grams 正。子配方消耗的是其成品质量，按子配方产出比例展开；整个图含未用配方也不得成环。同类组件可分行保留配方位置身份。成品质量不得超过组件质量总和，允许烹饪失水；采购 trim 不含烹饪失水，不提供完整化学质量平衡。

order：唯一 id、recipe 引用、正 output_grams。按质量线性缩放，不取整、不做最小批量或采购包装。每条叶路径保留配方与组件下标；合并采购按 ingredient 身份求和。展开单订单最多20000条叶，超过拒绝，输入最多100种原料/配方/订单和每配方30组件。

本版不管理库存、日历排程、补货、营养、替代品或价格版本。后续实秤修订、替代原料与标签版本可以接入 recipe/component 路径和采购量，而不是另造无关台账。

CLI 严格拒绝未知字段、重复JSON键、非法标识和非有限值，全部校验计算后创建新输出文件；目标存在或为符号链接时失败返回2，不覆盖。合成样例见 fixtures/SOURCES.md。

# 离线领料契约

在原有只读核算之外，`recipe-yield` 提供三个子命令管理一个本地领料库（ledger）：仓管员按工单从在库批次整单发料。原 `--source/--output` 核算命令行为不变，且不访问任何领料库。

## 命令与库

- `recipe-yield stock-init --ledger PATH --source LOTS.json`：在 PATH 创建新库。PATH 已存在（目录、文件或符号链接）时失败返回2，不覆盖。初始化失败尽力清理，不留半建目录。
- `recipe-yield stock-show --ledger PATH`：向 stdout 打印 `{"lots":[{"lot_id":...,"gross_remaining":...},...]}`，按 lot_id ASCII 升序，保留余额为零的批次。不扣料。
- `recipe-yield stock-issue --ledger PATH --source ISSUE.json`：校验并尝试整单发料；成功在 stdout 打印单行 JSON 收据并提交扣减，失败返回2且不产生任何扣减。

库是本地文件系统上的一个目录，含 `state.json`（全部批次余额与已提交请求）和 `lock`（进程间 `flock` 互斥文件）。同一台机器上的多个 CLI 进程可同时使用该库；所有读取在共享锁下进行，所有提交在排他锁下进行，任何进程都不会读到部分提交。库不引入外部服务或第三方运行依赖，不支持补仓、退料或未来预留：余额只减不增。

## 初始化输入

LOTS.json 为 `{"lots":[...]}`，0–200 条。每条字段恰为 `lot_id`、`ingredient`、`expires_on`、`gross_grams`、`price_per_gross_gram`、`tags`。lot_id 在库内唯一；同原料允许任意多批；初始化不要求配方目录。gross_grams 为正、price_per_gross_gram 非负（沿用十进制字符串语法）；tags 为 0–30 个不重复标记。expires_on 为合法公历 `YYYY-MM-DD`。ID 与标记沿用标识符语法。

## 领料输入

ISSUE.json 含原核算的 `ingredients`、`recipes`、`orders`（校验与数量上限不变），加上必填的 `request_id`（标识符）、`use_on`（合法公历日期）与 `restrictions`（0–200 条）。每份请求全部订单合计最多展开 200 条叶（原命令每订单 20000 条的上限仍适用于旧模式）。

`restrictions` 每条字段恰为 `order_id`、`path`、`forbidden_tags`。`order_id` 必须引用本请求的一张工单；`path` 为原报告证据中的字符串数组（如 `["soup:1","sauce:0"]`），必须指向该订单的一条真实叶——指向子配方节点或不存在的路径一律拒绝；同一订单同一路径不能出现两次。`forbidden_tags` 为 1–30 个不重复标记；未列出的叶不受限制。这些标记只用于仓内声明匹配，不是食品安全判定。

## 可用性与分配

每条叶按现有配方展开与净得率得到净需求与毛需求，不替代原料、不取整。批次对某叶可用，当且仅当：同原料、`expires_on >= use_on`（到期当天仍可用）、余额为正、批次标记与该叶禁用标记不相交。一条叶可拆用多批，一批也可分给多条叶，但必须同时满足全单所有叶的毛需求与每批余额。不存在全量可行分配时整单拒绝：不扣账、不占用 request_id，stderr 说明缺货。

可行分配不唯一时按字典序取最大：先按批次顺序（`expires_on` 升序、同日期按 lot_id ASCII 升序）比较各批次整单领用毛重构成的向量，第一处不同取用量更大的方案；该向量相同，再按叶顺序逐叶比较该叶各批次分配毛重（批次顺序不变），第一处不同同样取用量更大的方案。叶顺序为 order_id ASCII 升序，同订单内按路径组件下标序列逐项比较整数。未领用项按零处理。低价优先与逐路径先到先得都不是优先规则；目录价格与目录标记只用于旧核算，实领匹配、成本与实际声明以批次为准。

实现为精确有理数最大流：第一阶段按批次优先级增量增广得到各批次最大整单领用量，第二阶段按叶顺序逐坐标求保持余单可行的最大分配；不同原料互不连通，按原料分组求解后合并，与全局字典序最优等价。

## 收据

成功时 stdout 输出单行 JSON：`request_id`、`use_on`、`total_cost`、`lines`。lines 按叶顺序，每条含 `order_id`、`path`（字符串数组）、`ingredient`、`net`、`gross`、`trim`（毛重减净重）、`cost`、`tags`、`draws`。draws 按批次顺序只列正数领用的 `{lot_id,gross,cost}`；每笔成本为领用毛重乘该批次单价，叶成本与总成本按笔累加；叶 tags 取实际领用批次标记的并集，去重后按 ASCII 排序。余额、重量、金额一律输出约分后的整数或 `n/d` 字符串。

## 提交、重试与恢复

一次成功发料中，余额扣减、request_id 登记与原始收据三者原子生效（临时文件 + fsync + 原子替换 + 目录 fsync）。请求是否相同按解析后的完整领料 JSON 判断：忽略空白与对象键顺序，保留数组顺序与字符串值，十进制写法不同（如 `"8"` 与 `"8.0"`）视为不同内容。

- 同库同 ID 同内容的重试：优先返回逐字节相同的原始收据，不再扣料，即使后续发料已清空余额。
- 同 ID 不同内容：拒绝返回2，不改任何余额。
- 并发请求的结果与收据等价于某个串行提交顺序；同一请求的并发重试只扣一次。
- 成功收据在提交完成后才输出；输出中断不撤销提交。提交前终止进程不留部分扣减、不占用 request_id、不产生成功收据，重启后可重新提交。保障范围为本机进程中断与并发，不含整机断电。

## 严格性与退出码

三个子命令同样严格拒绝重复 JSON 键、未知字段、类型错误、无效日期与引用错误；库不存在、状态损坏或不能安全读取时失败。成功退出0（stock-init 成功不打印正文）；输入错误、缺货、已提交 ID 冲突、库不存在或不能安全读取等一律退出2，stderr 给出可辨原因，stdout 不伪造成功数据。

测试专用的内部故障注入点通过环境变量 `RECIPE_YIELD_CRASHPOINT`（取值 `before_commit` / `after_commit`）在提交前后精确终止进程，仅用于恢复语义测试，不是面向生产用户的参数。

# 印前标记核对契约

`recipe-yield label-preflight --source FILE --output REPORT` 在只读核算之外提供离线印前核对：沿订单的配方结构，按内部商品披露规则逐订单核算每个阈值标记的有效份额与声明依据，并对每张印刷批给出准印决定。这些标记只用于内部商品披露，不用于食品安全或法定合规判断。该命令不访问任何领料库，原核算命令与三个 stock 命令的契约保持不变，且不引入第三方运行依赖。

## 输入扩展

输入沿用原核算的 `ingredients`、`recipes`、`orders` 及全部字段语法、引用、数量与成环校验（含未被工单使用的配方），另加三个必填数组：

- `thresholds`：1–30 条 `{tag,min_share}`。`tag` 为标识符且表内唯一；`min_share` 为沿用原语法的十进制字符串，取值 `(0,1]`。只有列在此表的标记参与声明核算；标记不必出现在任何原料目录中。
- `declarations`：0–200 条 `{order_id,path,tag,action}`。`tag` 必须有阈值；`action` 仅允许 `suppress` 或 `restore`。`path` 为非空字符串数组（元素形如 `recipe:index`），从该订单根配方按组件下标逐级下行，可止于子配方组件或原料组件；继续穿过原料组件、下标越界或组件名与当前配方不符一律拒绝。同一 `(order_id,path,tag)` 只准一条声明。
- `print_jobs`：1–100 条 `{id,order_ids,tags}`。批 `id` 唯一；`order_ids` 至少一个真实订单，且每张订单必须且只能出现在一个印刷批中；`tags` 为印版上 0–30 个不重复标记，允许包含已不在阈值表中的合法标记（用于暴露陈旧印版）。

## 声明作用域与优先级

`suppress` 使该组件子树下的目录标记对该订单失效；`restore` 恢复按原料目录判断，不能给本身不带该标记的原料增加标记。作用状态沿路径向下继承，对同一订单、同一标记的多条前缀声明取最长匹配：最深（路径最长）的声明决定对应组件的状态，未被任何声明覆盖的组件按目录判断。共享子配方的某一次出现被声明，不影响它在其他路径上的出现；声明数组的书写顺序不影响结果。

## 份额、出现次数与第一路径

沿用原配方按子配方标称产出逐层缩放的口径。每张订单的分母 `total_net` 是其全部原料叶净重之和，而不是工单成品克数；声明不改变分母。对每个阈值标记独立核算：只加总最终有效的叶净重（`net`）并数有效叶的出现次数（`occurrences`，十进制整数字符串）；共享配方中的同一原料在不同路径出现分别计数，带多个标记的叶可分别贡献给多个标记。有效份额 `net / total_net` 精确达到阈值（含相等）才要求印该标记。`first_path` 是第一条有效叶的完整组件路径，按路径上各级组件的整数下标逐项比较取最小；无有效叶时为 `null`。

为支持反复嵌套的共享配方，核算不在内存物化全部叶：仅沿声明所在路径显式展开，无声明子树由按 `(配方, 缩放后用量, 抑制状态)` 记忆化的遍历回答。因此本命令不沿用旧命令每订单 20000 条叶的展开上限作为拒单条件；输入仍受原 8MB 文件大小与目录、组件数量上限约束。出现次数可以是任意精度的大整数。

## 报告与准印

成功时只发布一份新 JSON 报告到未存在的 `--output` 路径（目标已存在或为符号链接时失败返回 2，不覆盖、不留半份报告），并向 stdout 打印单行摘要 `{"approved":...,"orders":...,"print_jobs":...}`。报告顶层 `orders`、`print_jobs` 各自按 id 的 ASCII 顺序排列：

- 订单项为 `{id,total_net,required_tags,evidence}`。`evidence` 为 `{tag,net,occurrences,first_path}` 数组，按 `tag` 排序；阈值表中的零贡献标记同样列出，其 `net` 为 `"0"`、`occurrences` 为 `"0"`、`first_path` 为 `null`。重量一律输出约分后的整数或 `n/d` 字符串。
- 印刷批项为 `{id,approved,orders}`，其中 `orders` 按订单 id 排序，每项为 `{order_id,missing,extra}`。`missing` 是该订单应印但印版没有的标记，`extra` 是印版有但该订单不应印的标记，二者均按 ASCII 排序。印刷批可放行（`approved=true`）当且仅当批内每张订单的印版都与其应印标记集合恰好相等；把各单应印标记取并集来比对不算匹配。印版不匹配是正常审查结果，不是输入失败。

## 严格性与退出码

重复 JSON 键、未知字段、错误类型、越界数组、非法标识、无效引用或声明路径、重复身份（阈值标记、声明三元组、印刷批 id、订单的批归属）以及无法安全发布报告等情况一律退出 2，stderr 给出可辨原因，且不留下半份报告。成功退出 0。

# 返工对账契约

`recipe-yield rework-reconcile --source FILE --output REPORT` 在只读核算之外提供离线返工对账：根据实物流而非理论配方，重建某次内部质量核查当时能看到的结果，对比后来登记的结果，给出包件暂扣、已发包件追查与订单补货建议。它只供内部运营调度，不作食品安全或合规判断；不访问领料库，不改写任何收据或领料状态，原核算、`stock-*` 与 `label-preflight` 契约均保持不变。

## 输入与身份

输入是含 `receipts`、`orders`、`events`、`lot_ids`、`compare_to`、`as_known` 六个必填字段的 JSON 对象，沿用原标识符语法、十进制数量语法与 8MB 上限：

- `receipts`：1–100 张原 `stock-issue` 成功收据，逐字段沿用其类型（`request_id`、`use_on`、`total_cost`、`lines`，线内 `order_id`、`path`、`ingredient`、`net`、`gross`、`trim`、`cost`、`tags`、`draws`，笔内 `lot_id`、`gross`、`cost`）。收据中的数量是发料时写出的精确值，可为整数或约分后的 `n/d` 字符串，原样精确读取，不转成小数。`request_id` 在本次归档中唯一。同一 `(request_id, lot_id)` 的可用毛重是该收据所有相应 `draws.gross` 之和，不是全局批次余额；一张收据的额度不能挪给另一张收据。拒绝重复叶身份 `(order_id,path)`、同叶重复 `lot_id`、非正领用量，以及某叶 `draws.gross` 之和与 `line.gross` 不符的收据。由上游归档提供，不联网验真、不还原目录、不重算单价。
- `orders`：1–100 条 `{id,demand_grams}`，`id` 唯一，`demand_grams` 为正十进制字符串。这是发运订单，与收据中的加工工单属于不同命名空间。
- `lot_ids`：1–30 个不重复待核原料批次，每个须至少出现在一张收据的 `draws` 中。
- `events`：0–5000 条，数组位置即登记顺序（从 1 开始）。记录 `id` 在可见范围内全局唯一，各类 `id` 共用一个命名空间。
- `compare_to`、`as_known`：JSON 整数，`0 <= compare_to <= as_known <= len(events)`；0 表示尚无记录。只处理截至 `as_known` 的前缀，其后记录不参与校验与结论；收据与订单是两个截点共享的固定背景。

记录四类：

- `{id,kind:"mix",inputs,output_grams}`：投料均匀混成一批半成品，`id` 即半成品身份。`inputs` 为 1–30 条，每条是 `{request_id,lot_id,grams}`（取自领料收据）或 `{mix_id,grams}`（取自早于本批已生产的半成品）；同组内同一来源身份不得重复。`output_grams` 非负且不得超过投料总重，差额是工序失重。
- `{id,kind:"pack",mix_id,order_id,grams}`：从已生产的半成品分出一个包件，归给指定订单；`id` 即包件身份，包件不可再拆。`mix_id` 须引用登记位置不晚于该条的 mix，`order_id` 须为输入订单。
- `{id,kind:"ship",parcel_id}`：记录已发生的发运，须引用之前登记的包件，每包件至多发运一次；不扣半成品。对账不因当时本可暂扣而抹掉发运事实。
- `{id,kind:"amend",mix_id,inputs}`：最多 25 条。一次替换某已登记 mix 的整组投料来源与分量；**投料总重、原 mix 的位置与产出重不变**。新组内的半成品来源仍须早于被更正的 mix（而不是只早于这条 amend）。后一次更正替换前一次，不叠加扣料。更正从自己登记的位置起可知，不能改写更早截点的报告。

## 实物流约束

在任一可见记录前缀，以当时已知的更正重建实物流：同一收据来源累计投料不得超过其额度；同批半成品被后续混拌与打包取走的总量不得超过产出；更正须同时撤销旧组占用并计入新组，还要为当时已登记的其他用途留足量。任一可见前缀不合法即拒绝，不能靠后续更正掩盖中间超用。尚未使用的余额允许存在，不算交付。

## 归因与对账

命中 `lot_ids` 的收据材料按全重归入待核来源，其他收据材料按零计。每次混拌按混合前的实际投料重量比例传递归因，失重按相同比例分摊（投料比例 `r`、产出 `G` 则本批归因 `G*r`；此后取走 `g` 归因 `g*r`）。同一来源沿多路进入同一批时各路的实际投料份额都计入，不按有无路径去重、也不把整批重量算成来源重量。所有重量精确，报告用约分后的整数或 `n/d` 字符串。

分别在 `compare_to` 与 `as_known` 两个截点，为每个已登记包件计算归因克数。归因大于零时，已发包件为 `trace`、未发包件为 `hold`；归因等于零时，已发为 `shipped_clear`、未发为 `ready`。订单按**整包毛重**（不是归因克数）分四类累计，补货缺口为 `max(0, demand_grams - shipped_clear - ready)`，同一包件只计一次，超额交付不报负缺口。

## 报告与退出码

成功后只发布一份新 JSON 到未存在的 `--output`（目标已存在、为目录或符号链接时失败返回 2，不覆盖、不留半份报告），stdout 打印单行摘要 `{"changes":...,"orders":...,"parcels":...}`。报告为 `{before,after,action_changes}`，`before`/`after` 各含按 id ASCII 排序的 `parcels` 与 `orders`：

- 包件 `{id,order_id,grams,attributed_grams,action}`。
- 订单 `{id,demand_grams,ready,shipped_clear,hold,trace,gap_grams}`，无包件订单同样列出。
- `action_changes` 仅列处置变动，按包件 id 排序，项为 `{id,before,after}`；新增包件的 `before` 为 `null`；归因改变而处置不变不列。

正常的暂扣与缺口是结果，不是输入错误。重复 JSON 键、可见范围内未知字段、错误类型、非法引用、违反实物约束及无法发布等情况一律退出 2，stderr 给出可辨原因，且不覆盖既有文件、不留半份报告。
