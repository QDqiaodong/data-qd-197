# 配方核算契约

采购员输入 ingredients、recipes、orders 三个数组，厨师复核每条订单的配料来源路径。所有质量为克，金额使用同一调用者自定货币；数值输入为最多9位整数、6位小数的十进制字符串，精确有理数输出用整数或 n/d 字符串。

ingredient：唯一 id、yield (0,1]、price_per_gross_gram >=0、唯一 tags 数组。yield 将需用净料折算为采购毛料，trim 为这一步的损耗。标签只做原声明传播，不代表食品过敏安全判定。

recipe：唯一 id、正 output_grams、components。组件 kind 为 ingredient 或 recipe，ref 必须存在，net_grams 正。子配方消耗的是其成品质量，按子配方产出比例展开；整个图含未用配方也不得成环。同类组件可分行保留配方位置身份。成品质量不得超过组件质量总和，允许烹饪失水；采购 trim 不含烹饪失水，不提供完整化学质量平衡。

order：唯一 id、recipe 引用、正 output_grams。按质量线性缩放，不取整、不做最小批量或采购包装。每条叶路径保留配方与组件下标；合并采购按 ingredient 身份求和。展开单订单最多20000条叶，超过拒绝，输入最多100种原料/配方/订单和每配方30组件。

本版不管理库存、日历排程、补货、营养、替代品或价格版本。后续实秤修订、替代原料与标签版本可以接入 recipe/component 路径和采购量，而不是另造无关台账。

CLI 严格拒绝未知字段、重复JSON键、非法标识和非有限值，全部校验计算后创建新输出文件；目标存在或为符号链接时失败返回2，不覆盖。合成样例见 fixtures/SOURCES.md。

# 离线领料契约

在原有只读核算之外，`recipe-yield` 提供三个子命令管理一个本地领料库（ledger）：仓管员按工单从在库批次整单发料。原 `--source/--output` 核算命令行为不变，且不访问任何领料库。

## 命令与库

- `recipe-yield stock-init --ledger PATH --source LOTS.json`：在 PATH 创建新库。PATH 已存在（目录、文件或符号链接）时失败返回2，不覆盖。初始化失败尽力清理，不留半建目录。
- `recipe-yield stock-show --ledger PATH`：向 stdout 打印 `{"lots":[{"lot_id":...,"gross_remaining":...},...]}`，按 lot_id ASCII 升序，保留余额为零的批次。不扣料。
- `recipe-yield stock-issue --ledger PATH --source ISSUE.json`：校验并尝试整单发料；成功在 stdout 打印单行 JSON 收据并提交扣减，失败返回2且不产生任何扣减。

库是本地文件系统上的一个目录，含 `state.json`（全部批次余额与已提交请求）和 `lock`（进程间 `flock` 互斥文件）。同一台机器上的多个 CLI 进程可同时使用该库；所有读取在共享锁下进行，所有提交在排他锁下进行，任何进程都不会读到部分提交。库不引入外部服务或第三方运行依赖，不支持补仓、退料或未来预留：余额只减不增。

## 初始化输入

LOTS.json 为 `{"lots":[...]}`，0–200 条。每条字段恰为 `lot_id`、`ingredient`、`expires_on`、`gross_grams`、`price_per_gross_gram`、`tags`。lot_id 在库内唯一；同原料允许任意多批；初始化不要求配方目录。gross_grams 为正、price_per_gross_gram 非负（沿用十进制字符串语法）；tags 为 0–30 个不重复标记。expires_on 为合法公历 `YYYY-MM-DD`。ID 与标记沿用标识符语法。

## 领料输入

ISSUE.json 含原核算的 `ingredients`、`recipes`、`orders`（校验与数量上限不变），加上必填的 `request_id`（标识符）、`use_on`（合法公历日期）与 `restrictions`（0–200 条）。每份请求全部订单合计最多展开 200 条叶（原命令每订单 20000 条的上限仍适用于旧模式）。

`restrictions` 每条字段恰为 `order_id`、`path`、`forbidden_tags`。`order_id` 必须引用本请求的一张工单；`path` 为原报告证据中的字符串数组（如 `["soup:1","sauce:0"]`），必须指向该订单的一条真实叶——指向子配方节点或不存在的路径一律拒绝；同一订单同一路径不能出现两次。`forbidden_tags` 为 1–30 个不重复标记；未列出的叶不受限制。这些标记只用于仓内声明匹配，不是食品安全判定。

## 可用性与分配

每条叶按现有配方展开与净得率得到净需求与毛需求，不替代原料、不取整。批次对某叶可用，当且仅当：同原料、`expires_on >= use_on`（到期当天仍可用）、余额为正、批次标记与该叶禁用标记不相交。一条叶可拆用多批，一批也可分给多条叶，但必须同时满足全单所有叶的毛需求与每批余额。不存在全量可行分配时整单拒绝：不扣账、不占用 request_id，stderr 说明缺货。

可行分配不唯一时按字典序取最大：先按批次顺序（`expires_on` 升序、同日期按 lot_id ASCII 升序）比较各批次整单领用毛重构成的向量，第一处不同取用量更大的方案；该向量相同，再按叶顺序逐叶比较该叶各批次分配毛重（批次顺序不变），第一处不同同样取用量更大的方案。叶顺序为 order_id ASCII 升序，同订单内按路径组件下标序列逐项比较整数。未领用项按零处理。低价优先与逐路径先到先得都不是优先规则；目录价格与目录标记只用于旧核算，实领匹配、成本与实际声明以批次为准。

实现为精确有理数最大流：第一阶段按批次优先级增量增广得到各批次最大整单领用量，第二阶段按叶顺序逐坐标求保持余单可行的最大分配；不同原料互不连通，按原料分组求解后合并，与全局字典序最优等价。

## 收据

成功时 stdout 输出单行 JSON：`request_id`、`use_on`、`total_cost`、`lines`。lines 按叶顺序，每条含 `order_id`、`path`（字符串数组）、`ingredient`、`net`、`gross`、`trim`（毛重减净重）、`cost`、`tags`、`draws`。draws 按批次顺序只列正数领用的 `{lot_id,gross,cost}`；每笔成本为领用毛重乘该批次单价，叶成本与总成本按笔累加；叶 tags 取实际领用批次标记的并集，去重后按 ASCII 排序。余额、重量、金额一律输出约分后的整数或 `n/d` 字符串。

## 提交、重试与恢复

一次成功发料中，余额扣减、request_id 登记与原始收据三者原子生效（临时文件 + fsync + 原子替换 + 目录 fsync）。请求是否相同按解析后的完整领料 JSON 判断：忽略空白与对象键顺序，保留数组顺序与字符串值，十进制写法不同（如 `"8"` 与 `"8.0"`）视为不同内容。

- 同库同 ID 同内容的重试：优先返回逐字节相同的原始收据，不再扣料，即使后续发料已清空余额。
- 同 ID 不同内容：拒绝返回2，不改任何余额。
- 并发请求的结果与收据等价于某个串行提交顺序；同一请求的并发重试只扣一次。
- 成功收据在提交完成后才输出；输出中断不撤销提交。提交前终止进程不留部分扣减、不占用 request_id、不产生成功收据，重启后可重新提交。保障范围为本机进程中断与并发，不含整机断电。

## 严格性与退出码

三个子命令同样严格拒绝重复 JSON 键、未知字段、类型错误、无效日期与引用错误；库不存在、状态损坏或不能安全读取时失败。成功退出0（stock-init 成功不打印正文）；输入错误、缺货、已提交 ID 冲突、库不存在或不能安全读取等一律退出2，stderr 给出可辨原因，stdout 不伪造成功数据。

测试专用的内部故障注入点通过环境变量 `RECIPE_YIELD_CRASHPOINT`（取值 `before_commit` / `after_commit`）在提交前后精确终止进程，仅用于恢复语义测试，不是面向生产用户的参数。
